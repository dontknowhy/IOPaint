# i18n (UI + CLI localization)

Three surfaces, two catalog directories — the React bundle has its own runtime, the Python
side (Gradio config page + CLI) shares `iopaint/locales/*.json`:

| Surface | Code | Catalogs | Runtime | Detection |
|---|---|---|---|---|
| Web UI (React) | `web_app/src/` | `web_app/src/locales/*.json` | `i18next` + `react-i18next` + `i18next-browser-languagedetector` (`web_app/src/lib/i18n.ts`) | `localStorage["IOPAINT_LOCALE"]` → `navigator` → `en` |
| Gradio config page | `iopaint/web_config.py` | `iopaint/locales/*.json` (`web_config.*`) | Gradio's native `gr.I18n` (`iopaint/i18n.py`) | browser locale (exact match, else `en`) |
| CLI (typer) | `iopaint/cli.py`, `iopaint/runtime.py`, ... | `iopaint/locales/*.json` (`cli.*`) | `iopaint/i18n.py:cli_text()` | `IOPAINT_LOCALE` → `LC_ALL` → `LC_MESSAGES` → `LANG` → `en` |

The React catalog is deliberately separate: the React bundle is built by Vite (JSON is
imported/inlined), while the Python catalog is read at runtime from the installed package
and shipped via `setup.py:package_files` + `MANIFEST.in`. Sharing one directory would
couple the two build systems and the Python packaging for no real gain.

The Gradio and CLI namespaces live in the same files but stay separate — one key set per
surface, so a label written for a Gradio form ("Image Quality (...)", "GPU index ...") is
never reused as CLI option help.

## Adding a language

Both sides are registry-free — **dropping one JSON file registers a new language**:

1. React UI: add `web_app/src/locales/<bcp47>.json` (e.g. `ja.json`). `lib/i18n.ts` globs
   `../locales/*.json` via `import.meta.glob(..., { eager: true })`, so the file becomes a
   resource and shows up in **Settings → General → Language**. The display name comes from
   `Intl.DisplayNames` (each locale is shown in its own language), so no metadata file is
   needed.
2. Python side: add `iopaint/locales/<bcp47>.json` covering **both** `web_config.*` and
   `cli.*`. `iopaint/i18n.py:load_catalogs()` globs `locales/*.json`; the Gradio dict goes
   to `gr.I18n`, the CLI reads the same files through `cli_text()`.

Keys must match the canonical `en` catalog **exactly** (same key set, string values);
`en.json` on the React side and `build_en_catalog()` on the Python side are the sources of
truth. Parity is enforced by tests that iterate every locale file, so a new file is checked
automatically:

- `web_app/src/lib/i18n.test.ts` (`npm run test`)
- `iopaint/tests/test_i18n.py` (`pytest -m "not slow"`) — also checks that each translated
  `cli.*` string keeps the same `{placeholder}` set as its English twin

Missing translations fall back to `en` at runtime, but the parity tests fail on a partial
catalog, so keep the key sets identical.

## React UI conventions

- Nested JSON, dotted keys (i18next default separator): `t("shortcuts.undo")`,
  `t("settings.language.label")`.
- Interpolation with i18next syntax: `t("x.y", { count })` ↔ `"… ({{count}})"`.
- `en.json` is the canonical source for the compile-time key type: `src/i18next.d.ts` declares
  `CustomTypeOptions.resources = typeof en`, so a typo in a `t("…")` key fails `tsc`
  (`npm run build`).
- Components use `const { t, i18n } = useTranslation()`. Non-component call sites
  (`lib/states.ts` toasts, `lib/api.ts`) call `i18n.t(...)`, which reads the current language
  at call time.
- Don't translate identifiers or brand names: model names, `ControlNet`, `BrushNet`,
  `LCM LoRA`, `SD`/`SDXL`, sampler names, `INPAINT_NS`, keyboard key names.
- The browser default is detected automatically with an English fallback; CI/Playwright runs
  en-US, so English-text assertions in `iopaint/tests/test_webui.py` keep working. That test
  pins `locale="en-US"` on every browser context (`_new_context`) because the app follows
  `navigator.language` — a developer machine set to Chinese would otherwise render the UI in
  Chinese and fail the English selectors.

## Gradio page conventions

- `web_config.py` wraps every static label/value/tab in `i18n("web_config.<key>")`; `main()`
  passes `i18n=build_i18n()` to `demo.launch(...)`. `build_demo(config_file, i18n)` builds the
  `gr.Blocks` without launching it, so tests can serve it on a free port.
- `build_en_catalog()` assembles the English catalog **from `iopaint/const.py`'s `*_HELP`
  constants plus web_config literals**; `build_en_cli_catalog()` (same dict, `cli.*`
  namespace) reuses those same constants for the options shared with the CLI — so one
  English wording per help text, no drift. `iopaint/tests/test_i18n.py:test_en_catalog_tracks_const_help`
  locks the `web_config` mapping.
- `iopaint/i18n.py` is gradio-free (`build_i18n()` imports gradio lazily) so the validation
  tests can import it cheaply; `iopaint/locales/en.json` would override the code-assembled
  English catalog if present.
- **Dynamic backend messages** (`save_config`'s return value) are localized server-side:
  `save_config(..., request: gr.Request | None)` reads the request's `Accept-Language`,
  `pick_locale()` picks a catalog, and `translate(key, locale, **params)` formats the
  `web_config.msg_*` templates. The English templates are byte-identical to the pre-i18n
  strings, so logs/old assertions are unaffected.
  - `pick_locale()` only does **exact** matches (case-insensitive) and falls back to `en` —
    no `zh` → `zh-CN` subtag fallback. That mirrors the frontend, which only uses a locale's
    custom catalog when the locale matches exactly; otherwise its custom keys fall back to
    `en`. Matching the same way keeps the message language aligned with the rest of the UI.
  - Caveat: Gradio's in-app language picker (the gear → Language) is client-side only
    (`changeLocale` sets the svelte-i18n locale and sends nothing to the server), so it does
    **not** change the language of these server messages. They follow the browser's
    `Accept-Language`, which is also what the default detection uses, so the two agree unless
    the user overrides the language in the gear.
- `iopaint/tests/test_web_config_i18n.py` (Playwright) drives the real Gradio page and checks
  both halves: custom nested labels switch with the browser locale, and the save message
  comes back in the request's language. It serves Gradio's own bundled frontend, so unlike
  `test_webui.py` it needs no `iopaint/web_app` build; it skips when playwright is absent.

## CLI conventions

- **One namespace per surface**: `cli.command.*` (typer command descriptions), `cli.help.*`
  (option help, keyed by option name), `cli.error.*` (usage errors + startup/download
  failures). English lives in `build_en_cli_catalog()` (`iopaint/i18n.py`), everything else
  in `iopaint/locales/<locale>.json`.
- CLI text is pulled through `cli_text("cli.…", **params)` at the call site — help strings at
  import time (typer/click freeze `help=` when the command is built), error strings when the
  error is emitted. So the language is fixed by the environment **when `iopaint.cli` is
  imported**; `python -m iopaint --help` with a different `IOPAINT_LOCALE` needs a new
  process.
- Detection (`resolve_cli_locale()`): `IOPAINT_LOCALE` is explicit — an unknown value falls
  back to `en` instead of continuing down the chain; otherwise `LC_ALL` → `LC_MESSAGES` →
  `LANG`, with `zh_CN.UTF-8`/`zh-CN`/`zh` normalized to a `CATALOG` code (a bare language
  matches the single catalog of that language, so `LANG=zh_CN.UTF-8` picks `zh-CN`). Empty
  values count as unset; a set `C`/`POSIX` resolves straight to `en` and stops the chain, so
  `LC_ALL=C` forces English even when `LANG=zh_CN.UTF-8` (POSIX precedence). Other
  unrecognized system locales fall through to the next variable.
- Help strings that embed runtime data use `{placeholder}`s filled by the caller, never
  f-strings: that keeps the translated string able to move the data (e.g. `cli.help.model`
  takes the erase/diffusion model lists, `cli.help.model_dir` takes the resolved default
  cache path). `test_cli_catalog_placeholders_match_en` keeps every locale's placeholder set
  identical to the English one.
- Typer renders `help=` text as Rich markup, so a literal `[...]` in a help string must be
  written `\[...]` (escape only the opening bracket; `\]` would print a backslash). Keep the
  escape in every translation — without it Rich silently drops the bracketed text.
- Only user-facing text is translated: command/option help, usage errors and the failure
  messages printed on startup. `logger.info/warning/debug` progress and diagnostic logs stay
  English (they end up in bug reports), as do HTTP `detail` strings the WebUI renders (that
  surface has its own catalog). Exception: model-load and plugin errors raised in
  `helper.py`, `model/utils.py` and the plugins are also surfaced by the HTTP API
  (`ModelLoadError` / plugin `ValueError` in `api.py`), so they follow the **server's**
  environment, not the WebUI language — an English browser can see them in Chinese on a
  `LANG=zh_CN.UTF-8` server.
- Tests pin `IOPAINT_LOCALE=en` at the top of `iopaint/tests/conftest.py` — a developer
  machine with `LANG=zh_CN.UTF-8` would otherwise flip every English assertion in
  `test_cli*.py` / `test_device_fallback.py` / `test_helper_gaps.py`. The Chinese path is
  covered explicitly (`test_cli_text_follows_locale`, `test_resolve_cli_locale_*`, and
  `test_cli_help_uses_locale_in_subprocess`, which runs `python -m iopaint start --help` with
  `IOPAINT_LOCALE=zh-CN`).
