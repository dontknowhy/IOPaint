# i18n (web UI localization)

Two independent UIs, each with its own catalog directory and its own i18n runtime:

| UI | Code | Catalogs | Runtime | Detection |
|---|---|---|---|---|
| Web UI (React) | `web_app/src/` | `web_app/src/locales/*.json` | `i18next` + `react-i18next` + `i18next-browser-languagedetector` (`web_app/src/lib/i18n.ts`) | `localStorage["IOPAINT_LOCALE"]` → `navigator` → `en` |
| Gradio config page | `iopaint/web_config.py` | `iopaint/locales/*.json` | Gradio's native `gr.I18n` (`iopaint/i18n.py`) | browser locale (exact match, else `en`) |

The two catalogs are deliberately separate: the React bundle is built by Vite (JSON is
imported/inlined), while the Gradio catalog is read at runtime from the installed package
and shipped via `setup.py:package_files` + `MANIFEST.in`. Sharing one directory would
couple the two build systems and the Python packaging for no real gain.

## Adding a language

Both sides are registry-free — **dropping one JSON file registers a new language**:

1. React UI: add `web_app/src/locales/<bcp47>.json` (e.g. `ja.json`). `lib/i18n.ts` globs
   `../locales/*.json` via `import.meta.glob(..., { eager: true })`, so the file becomes a
   resource and shows up in **Settings → General → Language**. The display name comes from
   `Intl.DisplayNames` (each locale is shown in its own language), so no metadata file is
   needed.
2. Gradio page: add `iopaint/locales/<bcp47>.json`. `iopaint/i18n.py:load_catalogs()` globs
   `locales/*.json` and hands the whole dict to `gr.I18n`.

Keys must match the canonical `en` catalog **exactly** (same key set, string values);
`en.json` on the React side and `build_en_catalog()` on the Python side are the sources of
truth. Parity is enforced by tests that iterate every locale file, so a new file is checked
automatically:

- `web_app/src/lib/i18n.test.ts` (`npm run test`)
- `iopaint/tests/test_i18n.py` (`pytest -m "not slow"`)

Missing translations fall back to `en` at runtime, but the parity tests fail on a partial
catalog, so keep the key sets identical.

## React UI conventions

- Nested JSON, dotted keys (i18next default separator): `t("shortcuts.undo")`,
  `t("settings.language.label")`.
- Interpolation with i18next syntax: `t("x.y", { count })` ↔ `"… ({{count}})"`.
- `en.json` is the canonical source for the compile-time key type: `src/i18next.d.ts` declares
  `CustomTypeOptions.resources = typeof en`, so a typo in a `t("…")` key fails `tsc`
  (`npm run build`).
- Components use `const { t, i18n } = useTranslation()`. Non-component call sites
  (`lib/states.ts` toasts, `lib/api.ts`) call `i18n.t(...)`, which reads the current language
  at call time.
- Don't translate identifiers or brand names: model names, `ControlNet`, `BrushNet`,
  `LCM LoRA`, `SD`/`SDXL`, sampler names, `INPAINT_NS`, keyboard key names.
- The browser default is detected automatically with an English fallback; CI/Playwright runs
  en-US, so English-text assertions in `iopaint/tests/test_webui.py` keep working. That test
  pins `locale="en-US"` on every browser context (`_new_context`) because the app follows
  `navigator.language` — a developer machine set to Chinese would otherwise render the UI in
  Chinese and fail the English selectors.

## Gradio page conventions

- `web_config.py` wraps every static label/value/tab in `i18n("web_config.<key>")`; `main()`
  passes `i18n=build_i18n()` to `demo.launch(...)`. `build_demo(config_file, i18n)` builds the
  `gr.Blocks` without launching it, so tests can serve it on a free port.
- `build_en_catalog()` assembles the English catalog **from `iopaint/const.py`'s `*_HELP`
  constants plus web_config literals** — single source, so the CLI help and the Gradio help
  can't drift. `iopaint/tests/test_i18n.py:test_en_catalog_tracks_const_help` locks the
  mapping.
- `iopaint/i18n.py` is gradio-free (`build_i18n()` imports gradio lazily) so the validation
  tests can import it cheaply; `iopaint/locales/en.json` would override the code-assembled
  English catalog if present.
- **Dynamic backend messages** (`save_config`'s return value) are localized server-side:
  `save_config(..., request: gr.Request | None)` reads the request's `Accept-Language`,
  `pick_locale()` picks a catalog, and `translate(key, locale, **params)` formats the
  `web_config.msg_*` templates. The English templates are byte-identical to the pre-i18n
  strings, so logs/old assertions are unaffected.
  - `pick_locale()` only does **exact** matches (case-insensitive) and falls back to `en` —
    no `zh` → `zh-CN` subtag fallback. That mirrors the frontend, which only uses a locale's
    custom catalog when the locale matches exactly; otherwise its custom keys fall back to
    `en`. Matching the same way keeps the message language aligned with the rest of the UI.
  - Caveat: Gradio's in-app language picker (the gear → Language) is client-side only
    (`changeLocale` sets the svelte-i18n locale and sends nothing to the server), so it does
    **not** change the language of these server messages. They follow the browser's
    `Accept-Language`, which is also what the default detection uses, so the two agree unless
    the user overrides the language in the gear.
- `iopaint/tests/test_web_config_i18n.py` (Playwright) drives the real Gradio page and checks
  both halves: custom nested labels switch with the browser locale, and the save message
  comes back in the request's language. It serves Gradio's own bundled frontend, so unlike
  `test_webui.py` it needs no `iopaint/web_app` build; it skips when playwright is absent.
